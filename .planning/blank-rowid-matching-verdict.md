# Blank-Row-ID matching — investigation verdict (2026-06-09, ultracode workflow, 7 agents)

Source: workflow wf_e650f575-0bb (root-cause+repro, data-availability, design-authority, excel-ground-truth, adversarial attack, alternative design, synthesis). Repro script: /tmp/repro-blank-rowid.mjs (drove the REAL matcher modules).

## Root cause

For a blank-Row-ID row, the matcher's ONLY recovery strategy is Pass 3 of buildImportPlan: an exact-equality filter of the incoming row's identityVectorFingerprint against each leftover stored marker's baseline (src/services/rowImportMatcher.js:146, verified). The identity vector includes Notes (src/services/rowFingerprint.js:122-127), and the baseline is restamped only at import-apply/create or export — never on app edits (src/PDFViewer.jsx:13584-13587, 13646-13652) — so when the user changed the Excel note to "not car", the incoming fingerprint stopped matching the baseline stamped when notes were blank, candidates=0, and rowImportMatcher.js:161 emitted {decision:'new-row', action:'create'} — the duplicate. The both-sides conflict guard is structurally unreachable for this case: it only downgrades decisions whose action is already 'apply' (src/services/buildScopeImportPlans.js:178, verified — `if (d.action === 'apply' && appValuesByMarkerId && d.markerId ...)`), so a row that fails fingerprint recovery can never become a 'conflict'. The app-side "car" edit is irrelevant to the mismatch — a reproduction driving the real modules (/tmp/repro-blank-rowid.mjs) proved an Excel-ONLY edit duplicates identically (Control B), so the bug class is "any Excel edit to item/entity/notes/any answer on a blank-ID row duplicates". In the same import the orphaned original entered candidateDeletes (rowImportMatcher.js:178-180); it survived as a review item only because it was never exported (wasReceivedByExcel requires exportedAt, src/services/excelExportAck.js:50-52). Higher-severity proven variant (Variant C): any successful export stamps exportedAt on EVERY marker (excelExportAck.js:34-41), after which the same scenario silently auto-trashes the original (PDFViewer.jsx:13703-13704 manual, 14292-14293 auto; 30-day tombstone, restorable) while creating the duplicate. Decisive line: rowImportMatcher.js:146 (exact-fingerprint-only blank recovery) falling through to :161, with the conflict guard gated at buildScopeImportPlans.js:178.

## Data availability

YES on both read paths, NO persistence today. Local and OneDrive/Graph imports both download/read the complete saved file and parse it with the identical exceljs loop; exceljs hands the TRUE 1-based sheet row number to the existing callback on both paths — verified at src/PDFViewer.jsx:14850 (manual) and 15023 (auto/Graph; Graph path downloads the whole binary via excelGraphService.js:124-197 first) — but the code discards rowNumber and compacts rows into jsonData, so today's index = "nth non-empty row", not sheet row (eachRow without includeEmpty skips empty rows). Capturing the real row number is a one-line change per loop. The Graph usedRange API (which returns absolute addresses) is used only as a live-sync change detector (PDFViewer.jsx:15378-15391), never as matcher input. The matcher receives zero position: rows are {rowIdCell, values} and stored[] carries only markerId + content fingerprints + copy lineage (buildScopeImportPlans.js:130-151, verified). Nothing positional is persisted anywhere: per-marker excelSync holds fingerprints/lineage only (excelIdentityRecord.js:40-57), the baseline store is one hash string per (pdfId, templateId) (excelSyncBaselineStore.js:30-57), and there is no previous-sheet-layout snapshot in any store. Save semantics are favorable: locally a chokidar watcher with awaitWriteFinish fires only on completed saves (electron-main.js:1105-1123); OneDrive triggers a full re-download — imports only ever see complete saved snapshots, and the exact parsed snapshot is in hand at the same moment identity records are stamped. Two caveats: excelSync is DEVICE-LOCAL (not in the Supabase mapper, documentSurveyMarkerMapper.js:18-60), so any positional memory is per-device unless moved to the shared store; and a workbook-resident snapshot cannot work because writeback is gated off, so an in-file layout could only ever reflect the last EXPORT — exactly excluding the user-created blank-ID rows the proposal targets. Cheapest persistence: stamp lastSeenRowNumber (+ ingest sequence) into the existing per-marker excelSync record at the existing stamping sites — rides existing persistence for free, ~40-60 bytes/marker (<6% growth at the 24,450-marker baseline), no new store needed.

## User plan verdict

RIGHT (and at the theoretical ceiling): xlsx has no per-row identity — CT_Row carries only a row index, Microsoft's revision extensions stamp GUIDs on sheets/tables/columns but pointedly not rows, Graph has no row-level diff, and even live Office.js denies row identity — so position + content over two full saved snapshots is the best physically possible signal set for blank-ID rows; his "previous layout = layout as of the last save the app ingested" framing is exactly correct for the save-only constraint; his elimination example (rows 5 and 7) works and is impossible for today's content-only matcher; and the whole idea is not a new design — it is an implementation strategy for the already-approved Amendment (b) alias rowLocator (PLAN.md:234-236) and directly answers the plan's open "row locator instability" risk (PLAN.md:253). It also strictly improves copy-paste-above (today the pasted copy steals the original marker). BREAKS, severity-weighted: (HIGH, data corruption) rule (a)'s value-blind "same position + nothing else changed = same row even if every value changed" silently grafts a Survey Marker's pin, note history, and identity onto a genuinely different row when the user deletes a row and types a new one in the same slot — byte-indistinguishable from an in-place edit, and likeliest precisely when Item names repeat (an explicitly allowed pattern); worse, every match restamps the content baseline (buildScopeImportPlans.js:162-167), so a wrong graft self-perpetuates and can never self-correct. (HIGH, data corruption) rule (b)'s pure elimination silently mis-binds on delete-one-add-one in the same save (and the cross-sheet-paste sub-variant), because a snapshot diff cannot verify the conservation assumption elimination depends on; position must also never outrank an exact unique content match (two rows swapping content would otherwise swap pins). (MEDIUM, regression) rule (c)'s "give up and create a duplicate" arm contradicts the locked design — ambiguity with stored candidates always goes to review (PLAN.md:235; the shipped matcher already does this at rowImportMatcher.js:156-159) — and a duplicate re-exposes the original to the candidate-delete/auto-trash path. (LOW, gap) cold start: the positional scheme fixes nothing until one save has stamped a layout, while a storage-free field-overlap slice fixes tonight's bug immediately. Where lanes disagreed, the attacker's stricter gates win on evidence: its scenarios were probe-driven against the real modules, and the corruption branches it found are real; the alternative design's per-marker-stamp storage choice beats the attacker's whole-snapshot/IndexedDB concern by mooting it (no snapshot store, no short-hash, ~40-60 B/marker).

## Recommended design (tiers)

Layered matcher, all tiers per scope inside buildImportPlan; "leftovers" = stored markers not yet matched; "blanks" = blank-Row-ID rows. Strict precedence (closes the swap/mixed-population attacks): Row-ID tokens > exact unique content fingerprint > corroborated position/elimination, always over leftovers only. TIER 0 — Row ID token resolution, unchanged (rowImportMatcher.js:97-135). TIER 1 — pending-writeback alias (future, governed by PLAN.md:235); the Tier 3 positional stamp becomes its rowLocator. TIER 2 — exact identity fingerprint, made GROUP-AWARE: group blanks and leftovers by fingerprint; 1×1 → apply as today; N×M with trusted positions → assign same-slot first then preserved relative order, residue 1×1 by elimination, anything else → 'ambiguous-identity' review; never create while same-fingerprint leftovers remain (also fixes the latent first-row-wins nondeterminism at rowImportMatcher.js:142-162). TIER 3 — positional slot for content-changed rows (slice 2): requires (i) lastSeenRowNumber + ingestSeq stamped from the PREVIOUS ingested save, (ii) anchor order-consistency (all token/exact matches with stored positions remain monotone — honors the Codex lock "no positional guess on untrusted order"), (iii) slot agreement using the offset of flanking anchors (insert-shift-proof, replacing the user's literal absolute position), (iv) bidirectional uniqueness. Then: ≥1 unchanged non-blank identity field vs stored fieldFingerprints → APPLY (decision 'missing-rowid'), which the existing conflict guard auto-downgrades to 'conflict' review on both-sides edits; ZERO unchanged fields (total rewrite at same slot) → 'moved-or-replaced' REVIEW naming the marker, never silent — this is the mandatory amendment to the user's rule (a). Any precondition fails → tier skipped. TIER 4 — unique elimination by field overlap (the minimal slice, no storage): pair an unmatched blank and a leftover sharing ≥1 NON-BLANK identity field fingerprint (blank==blank never counts), unique in both directions, iterated to fixpoint; ADDITIONALLY gated by a conservation check (the scope's row-count delta is explained by matched rows) and preceded by cross-scope fingerprint reconciliation so a cut+paste between sheets is recognized as a move, not eliminated against (closes the attacker's S7 sub-variant — this gate is added on top of the alternative proposal because the attacker's corruption branch is real). Pairs emit 'missing-rowid'/apply → conflict guard runs. TIER 5 — fall-through: zero overlap with all leftovers → 'new-row' create (Amendment #2 preserved); ≥2 plausible pairings either direction → 'ambiguous-identity' review listing candidates, which auto-shields them from candidateDeletes (rowImportMatcher.js:172-180); the user's rule (c) duplicate arm is dropped — candidates-exist + indistinguishable = review, per PLAN.md:235. TIER 6 — candidateDeletes triage unchanged, plus three hardenings: an isPlacedSurveyMarker guard on the Row-ID-branch auto-delete (currently absent at PDFViewer.jsx:13699-13709), a delete-grace window spanning consecutive saves, and AutoSave/save-burst debounce (closes the mid-reorganization and Variant-C interplay attacks). DATA CAPTURE (slice 2): record exceljs rowNumber in both parse loops (PDFViewer.jsx:14850, 15023) without disturbing jsonData indices; thread sheetRowNumber through rows[] and lastSeenRowNumber/ingestSeq through stored[]; stamp into the identity record at the existing attachment point (buildScopeImportPlans.js:162-173) so it persists for free via the existing wholesale excelSync stamping — no new store, no whole-layout snapshot, no short hashes; fail closed/degrade to Tiers 4-5 when stamps are missing or stale (covers cold start and multi-device divergence, since excelSync is device-local). REVIEW UI: add a third choice "this is a different row — create a new Survey Marker" to the conflict/ambiguity dialog (the current keep-app/use-Excel pair cannot express delete-and-replace). Long-term: enable Row-ID writeback (rowIdWritebackQueue.js is built with no callers) — the only mechanism above this heuristic ceiling; every token written back shrinks the population these tiers serve. Gate everything on the Codex-R4 required tests plus T1-T15 from the design lane (sorted-before-writeback → review; repeated save ×N → one marker; the verbatim bug steps → one 'conflict' review with empty candidateDeletes).

## Minimal slice (fixes tonight's bug)

Tier 4 alone, implemented entirely in src/services/rowImportMatcher.js (plus its test file) — zero new storage, zero executor changes, works on cold start. Extend Pass 3: for a blank-ID row with zero exact-fingerprint candidates, attempt recovery by per-field fingerprint overlap against leftover markers — fieldFingerprints are already delivered in stored[] (buildScopeImportPlans.js:145, verified). Pair only when the row and marker share ≥1 NON-BLANK identity field (field fingerprint equal AND not equal to the precomputed empty-canonical fingerprint, so blank==blank never counts) AND the pairing is unique in both directions; emit the EXISTING decision 'missing-rowid' with action 'apply' so executors need no changes. The existing Amendment-#6 conflict guard (buildScopeImportPlans.js:178-197, verified) then automatically downgrades both-sides edits to the shipped 'conflict' review — the user's exact bug becomes the keep-app("car")/use-Excel("not car") dialog he expected. Multiple plausible candidates → 'ambiguous-identity' review (existing path, rowImportMatcher.js:156-159), never create. Safety side effects for free: the matched marker joins matchedMarkerIds and leaves candidateDeletes (rowImportMatcher.js:178-180), and review-listed candidates are shielded by the existing exclusion (:172-180) — making the proven Variant-C silent auto-trash impossible for this shape. Verification gate: tests T1 (verbatim bug steps → one 'conflict' decision, conflictFields=['notes'], candidateDeletes=[]), T5 (Excel-only edit → clean whitelisted apply, no duplicate), T6 (Variant-C guard), T9 (repeated save ×N → one marker), T10 (genuinely new rows still create — Amendment #2 regression guard), T12 (blank-overlap exclusion), T13 (order independence), T14 (pairing emits 'apply' BEFORE the conflict guard so the guard stays reachable), T15 (no positional data required); baseline 1153 pass / 0 fail / 6 skipped must hold via node scripts/run-node-tests.mjs. Known residual accepted in this slice: delete-a-row-then-retype-same-Item-at-same-slot is observationally identical to an edit and will re-attach (it flows to a conflict review when both sides changed, silent apply when one-sided) — only Row-ID writeback or the slice-2 'different row' review choice can do better, and the status quo (duplicate + possible auto-trash) is strictly worse.

## Open product questions for Isaiah

- Review dialog third choice: approve adding 'this is a different row — create a new Survey Marker' alongside keep-app/use-Excel? Without it the app can never honestly express delete-and-replace-at-the-same-slot, and the conflict dialog will occasionally pair two rows that are genuinely different.
- Amendment to his rule (a): confirm that a same-position row where EVERY field changed goes to a review prompt instead of silently counting as the same row. His literal rule says 'same even if every visible value changed' — the investigation shows that branch silently grafts a placed Survey Marker onto a replacement row and the mistake self-perpetuates.
- Amendment to his rule (c): confirm dropping the 'create a duplicate' arm — when stored candidates exist, indistinguishable rows always go to 'Needs your choice' (this matches his own locked PLAN decision; silent create remains only for genuinely new rows).
- Row-ID writeback timing: when may the Stage-0 gate flip on (e.g. after the live Business-M365 test), and is eager local writeback acceptable whenever Excel is detected closed? This is the only permanent cure; every heuristic tier exists to cover the writeback gap.
- Delete-grace window: how long (or how many consecutive saves) should a disappeared row be held before auto-trash of an exported marker? Today a single mid-reorganization save (cut row, save, paste, save) can auto-trash; AutoSave on cloud files saves every few seconds and multiplies this.
- Auto-delete hardening: should placed Survey Markers be exempt from auto-trash entirely (always review) on the Row-ID path, as they already are on the legacy path? This changes shipped delete semantics.
- Multi-device scope: positional memory would live per-device (sync identity records are not in the cloud store today). Accept single-device positional matching with safe degrade-to-review on other devices, or invest in moving identity records to the shared store first?


## AMENDMENTS — Isaiah's decisions (2026-06-09, late session) — GOVERNING over the sections above

1. **NO third review choice.** The conflict prompt stays exactly keep-app / use-Excel. The "this is a different row" option is REJECTED.
2. **Total rewrite at a stable slot = SILENT MATCH, no prompt.** When a blank-Row-ID row sits at the same sheet position, the surrounding layout is otherwise stable (anchors monotone, row-count delta explained), and every visible field changed, treat it as the SAME row with updated values — his rename example ("test"→"car", single-field row) governs. The 'moved-or-replaced' review from the recommended design is DROPPED. Accepted residual: a true delete+retype-in-same-slot between two saves will re-attach the old Survey Marker (pin keeps old location, takes new values) — Isaiah explicitly accepted this; it is rare, manually fixable, and vanishes once Row-ID writeback turns on.
3. **Delete-and-replace NEVER prompts.** Excel deleting a received row and adding another is two sanctioned silent operations; no "needs your choice" for that shape. Review prompts remain ONLY for: both-sides edits (existing conflict flow) and genuinely consequential ambiguity (multiple non-identical candidates either direction).
4. **Identical-twin groups pair in order, silently** (example 5): N byte-identical rows vs N identical-baseline markers → order-preserving assignment (same-slot first), zero creates, zero prompts — assignment is data-inconsequential, pins preserved.
5. **Full implementation green-lit in sequence** (no push until live-tested): Tier-4 field-overlap recovery → position capture/persistence → group-aware + positional tiers per the amendments → one-import delete-grace window (flagged for his veto: a delete now takes effect one save later) → scenario suite incl. his five verbatim examples.

# Phase 15 — UI Design Contract

> Visual and interaction contract for the line/arrow curvature midpoint handle, curved-path render, and six-style arrowhead enum. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase is UI-LIGHT.** No new pages, no forms, no toolbar picker (Phase 16 owns the picker). The contract below locks down three visual surfaces only:

1. The new midpoint curvature handle (3rd handle on selected lines/arrows)
2. The curved-line render (SVG `<path>` branch replacing the `<line>` branch when `data.midpoint` is present)
3. The six arrowhead style visual forms (programmatically set in Phase 15, picker ships in Phase 16)

Sections not applicable to this phase (typography, copywriting beyond one optional tooltip, empty/error states, registry) are marked explicitly as **N/A — phase boundary**.

## Spacing Scale

**N/A — phase boundary.** Phase 15 introduces zero layout surfaces. Handle size and arrowhead size scale from stroke width + zoom inverse, not from a design spacing scale.

**Size-from-math tokens (canonical for Phase 15):**

| Token | Formula | Usage |
|-------|---------|-------|
| Endpoint handle radius | `r = 7 × √(inverseScale)` | Existing p1/p2 handles — `SVGAnnotationLayer.jsx:1774`. **Do not alter.** |
| Midpoint handle radius | `r = 5 × √(inverseScale)` | New 3rd handle — ~71% of endpoint size. Reads as "secondary control". |
| Drop-shadow offset | `1 × √(inverseScale)` px | Handle shadow — existing pattern at `:1776`. Midpoint reuses verbatim. |
| Drop-shadow blur | `3 × √(inverseScale)` px | Handle shadow — existing pattern at `:1776`. Midpoint reuses verbatim. |
| Arrowhead base size | `headSize = max(8, strokeWidth × 3)` | Existing formula at `svgAnnotationRenderers.jsx:163`. **All 6 styles scale from this.** |
| Snap-to-straight drag threshold | `10px` (SVG page coordinates) | Hardcoded in `lineGeometry.js` — silent snap, no visual indicator |
| Render hysteresis | `1px` (SVG page coordinates) | Hardcoded in `lineGeometry.js` — renders `<line>` instead of near-straight `<path>` |

**Zoom-constant sizing invariant:** All handle dimensions (radius, stroke width, shadow) use `vectorEffect="non-scaling-stroke"` OR inverse-scale multipliers so the visual weight is constant across zoom levels. Arrowhead dimensions scale with the annotation's stroke width (so arrowheads grow with thicker lines) but also honor `non-scaling-stroke` where they have stroke styling (V_SHAPE, OPEN_CIRCLE, OPEN_TRIANGLE, HORIZONTAL_LINE).

## Visual Specifications (phase-specific sections)

### Section A — Midpoint Curvature Handle

**Placement:** On the rendered curve at parametric position `t=0.5` (via `getPointOnCurve(start, end, midpoint, 0.5)`) when the line is curved. On the geometric midpoint (via `getMidpoint(start, end)`) when the line is straight. Handle is part of the selection-wrapper `<g>` alongside p1/p2, so it inherits selection visibility gating.

**Visual form:** Same as existing endpoint handles with a smaller radius.

| Attribute | Value | Rationale |
|-----------|-------|-----------|
| Element | `<circle>` | Matches p1/p2 — unified visual language |
| `r` | `5 × √(inverseScale)` | ~71% of endpoint `7 × √(inverseScale)`. "Secondary control" cue. |
| `fill` | `#ffffff` | Same as p1/p2 |
| `stroke` | `#4a90e2` | Same as p1/p2 |
| `strokeWidth` | `1.5` | Same as p1/p2 |
| `vectorEffect` | `"non-scaling-stroke"` | Zoom-constant ring weight |
| `filter` (drop-shadow) | `drop-shadow(0 ${1 × handleIs}px ${3 × handleIs}px rgba(0,0,0,0.15))` where `handleIs = √(inverseScale)` | Same as p1/p2 |
| `cursor` | `grab` (idle), `grabbing` (during drag) | Unified grab semantics with p1/p2 |
| `pointerEvents` | `auto` | Required for drag dispatch |

**Tether:** NONE. Do not draw a dashed line from the straight baseline to the midpoint handle. The handle sits on the curve; the curve is the visual feedback.

**Visibility rules:**

| Annotation state | Midpoint handle visible? |
|------------------|---------------------------|
| Unselected line/arrow (idle) | NO — zero chrome, same as today |
| Unselected line/arrow (hover) | NO — hover-reveal is Phase 18 |
| Selected line/arrow (straight, `data.midpoint` unset) | YES — positioned at geometric midpoint |
| Selected line/arrow (curved, `data.midpoint` set) | YES — positioned at `t=0.5` on the curve |
| Selected line/arrow (in edit mode via double-click) | N/A — no edit-mode entry for lines/arrows in Phase 15 |

**Differentiation from endpoint handles:** Size only. Same shape, same fill, same ring color. The ~29% size reduction is the visual signal. Do **not** introduce a different fill color, a square shape, an icon inside, or a center dot — those all violate the "combined-tools convention" lock in 15-CONTEXT.md Area 1.

**Dispatch:** New `handleId = 'midpoint'` dispatched through the existing `handleHandlePointerDown(e, handleId)` hook alongside `'p1'` and `'p2'`. Handle element emits `e.stopPropagation()` before dispatch, matching the pattern at `SVGAnnotationLayer.jsx:1791`.

### Section B — Curved Line Render

**Branch selection (top of `renderLine`):**

```
isCurved = data.midpoint
           && distanceToLineSegment(data.midpoint, { x: x1, y: y1 }, { x: x2, y: y2 }) > 1
```

The 1px render-hysteresis clamp lives HERE (not in the math library) — the library exports `distanceToLineSegment`, the renderer interprets the threshold.

**Straight branch (unchanged):** Existing `<line>` at `svgAnnotationRenderers.jsx:186-198`. Byte-identical to v2.2 render. This is the no-regression contract — any pixel delta on a straight line between pre- and post-Phase-15 is a bug.

**Curved branch (new):**

| SVG output | Value |
|------------|-------|
| Primary element | `<path d={getCurvedPath({x:x1,y:y1}, {x:x2,y:y2}, data.midpoint)}>` |
| `d` attribute format | `"M sx sy Q cx cy ex ey"` — emitted verbatim by `getCurvedPath` |
| `stroke` | `obj.stroke \|\| '#000'` — same as straight branch |
| `strokeWidth` | `obj.strokeWidth \|\| 2` — same as straight branch |
| `strokeLinecap` | `"round"` — same as straight branch |
| `fill` | `"none"` — critical; without it the bezier fills with black |
| `opacity` | `obj.opacity ?? 1` — same as straight branch |

**Shortening for arrows (curved arrow):** When `isArrow && isCurved`, the path still emits as a full `M Q` bezier to the endpoint. The arrowhead overlays the endpoint tip. **Do not attempt to shorten the curved path** (unlike the straight arrow branch at `:166-167` which shortens `lineEndX/Y` by `headSize/3`). Curve shortening requires parametric t-solve on the bezier and the visual gain is negligible compared to the implementation risk. The arrowhead's inherent solid fill hides the ~1-3 px stroke poke-through at the tip.

**Key continuity:** `<g key={key}>` wrapper for arrows, `<path key={key}>` direct for non-arrow curved lines. Keys match the straight branch's pattern.

### Section C — Six Arrowhead Styles (Visual Forms)

All six styles share:

- **Tip anchor:** Centered on `(tipX, tipY)` — the endpoint tip of the line/arrow.
- **Rotation anchor:** `transform="translate(tipX,tipY) rotate(angleDeg)"`. Angle comes from:
  - Straight: `angleDeg = Math.atan2(y2 - y1, x2 - x1) × (180 / π)`
  - Curved: `angleDeg = getCurveEndAngle(start, end, midpoint)` (already returns degrees per `lineGeometry.js:125`)
- **Base size:** `headSize = max(8, strokeWidth × 3)` — sourced from `svgAnnotationRenderers.jsx:163`. All geometry scales proportionally.
- **Color:** Inherits `obj.stroke` (`strokeColor` in the render scope) for both fill and stroke roles — never introduces a new color.
- **Container:** Each style renders as the children of a single `<g transform="translate rotate">` so the local coordinate system has the tip at origin and the arrow direction along `+x`. Geometry below is specified in that local frame.

The six styles below are **the complete locked visual contract** for Phase 15. Phase 16's picker UI must render exactly these six and offer zero additional variants.

#### C.1 — `NONE` (`'none'`)

**Visual:** Nothing — emit no arrowhead element. The line stops at its endpoint with `strokeLinecap="round"` rounding.

**SVG output:**
```jsx
return null;
```

**Used for:** Default on `tool === 'line'` annotations. Picker option shown as "None" in Phase 16.

**Line-shortening:** NONE (keep full line extent).

---

#### C.2 — `SOLID_TRIANGLE` (`'solidTriangle'`)

**Visual:** Filled equilateral-ish triangle, base-at-back, tip-at-front. Reads as a classic arrowhead. This is the **default for `tool === 'arrow'`** and matches the pre-Phase-15 visual identically.

**Local-frame geometry** (tip at origin, arrow direction = +x):

| Vertex | Coord |
|--------|-------|
| Back-upper | `(-headSize × 2/3, -headSize / 2)` |
| Tip | `(headSize × 1/3, 0)` |
| Back-lower | `(-headSize × 2/3, +headSize / 2)` |

Wait — verify against existing code. Existing renderer at `svgAnnotationRenderers.jsx:178`:

```
points={`${-headSize / 3},${-headSize / 2} ${headSize * 2 / 3},0 ${-headSize / 3},${headSize / 2}`}
transform={`translate(${x2},${y2}) rotate(${angleDeg})`}
```

Tip is at `+headSize × 2/3` (forward of the translate anchor), back is at `-headSize / 3`. The `translate(x2, y2)` places the triangle so its centroid is near `(x2, y2)` but the tip extends **past** `(x2, y2)`.

**Locked geometry for Phase 15 (matching existing implementation, do not change):**

| Vertex (local frame) | Coord |
|----------------------|-------|
| Back-upper | `(-headSize / 3, -headSize / 2)` |
| Tip | `(+headSize × 2/3, 0)` |
| Back-lower | `(-headSize / 3, +headSize / 2)` |

**SVG output:**
```jsx
<polygon
  points={`${-headSize / 3},${-headSize / 2} ${headSize * 2 / 3},0 ${-headSize / 3},${headSize / 2}`}
  fill={strokeColor}
  transform={`translate(${tipX},${tipY}) rotate(${angleDeg})`}
/>
```

**Used for:** Default on `tool === 'arrow'`. Preserves v2.2 visual identically.

**Line-shortening (straight arrow only):** Existing formula `lineEndX = x2 - (headSize / 3) × cos(angleRad)`, `lineEndY = y2 - (headSize / 3) × sin(angleRad)`. Apply to straight arrows only; curved-arrow branch does NOT shorten (see Section B).

---

#### C.3 — `V_SHAPE` (`'vShape'`)

**Visual:** Two stroked lines forming a V, converging at the tip, opening backward. Stroke-only (no fill). Reads as a lighter, sharper arrowhead.

**Local-frame geometry:**

- Arm length: `armLength = headSize` (equals base formula output — NOT `baseSize` from legacy — see head-size unification below)
- Arm spread angle: `armAngle = π/6` (30° off the line axis, each side)
- Arm 1 back point: `(-armLength × cos(armAngle), -armLength × sin(armAngle))` → ≈ `(-0.866 × headSize, -0.5 × headSize)`
- Tip: `(0, 0)` (local origin — the arrow's tip endpoint)
- Arm 2 back point: `(-armLength × cos(armAngle), +armLength × sin(armAngle))` → ≈ `(-0.866 × headSize, +0.5 × headSize)`

**SVG output:**
```jsx
<polyline
  points={`${-headSize * Math.cos(Math.PI/6)},${-headSize * Math.sin(Math.PI/6)} 0,0 ${-headSize * Math.cos(Math.PI/6)},${headSize * Math.sin(Math.PI/6)}`}
  fill="none"
  stroke={strokeColor}
  strokeWidth={Math.max(2, obj.strokeWidth || 2)}
  strokeLinecap="round"
  strokeLinejoin="round"
  transform={`translate(${tipX},${tipY}) rotate(${angleDeg})`}
/>
```

**Stroke width:** `max(2, obj.strokeWidth || 2)` — matches the legacy `createArrowhead` V_SHAPE branch (`PageAnnotationLayer.jsx:392`). Prevents V from becoming invisibly thin on 1px lines.

**Line-shortening:** NONE — the V sits at the tip, the line can end flush without poking through (the V opens backward).

---

#### C.4 — `OPEN_CIRCLE` (`'openCircle'`)

**Visual:** Hollow ring centered on the tip. Reads as a terminator / endpoint marker. Symmetric — rotation-invariant but rotation is still applied for consistency.

**Local-frame geometry:**

- Radius: `radius = headSize / 2`
- Center: `(0, 0)` — placed directly at the tip endpoint

**SVG output:**
```jsx
<circle
  cx={0} cy={0} r={headSize / 2}
  fill="transparent"
  stroke={strokeColor}
  strokeWidth={Math.max(2, obj.strokeWidth || 2)}
  transform={`translate(${tipX},${tipY}) rotate(${angleDeg})`}
/>
```

**Stroke width:** `max(2, obj.strokeWidth || 2)` — legacy `createArrowhead` OPEN_CIRCLE branch (`PageAnnotationLayer.jsx:413`).

**Line-shortening:** Line may extend into the circle center; the ring's stroke + the line's `strokeLinecap="round"` combine visually cleanly. No explicit shortening required.

---

#### C.5 — `OPEN_TRIANGLE` (`'openTriangle'`)

**Visual:** Same triangle shape as SOLID_TRIANGLE (C.2) but stroke-only — hollow triangle. Reads as a technical / diagrammatic arrowhead.

**Local-frame geometry:** Identical vertex coordinates to SOLID_TRIANGLE (C.2).

**SVG output:**
```jsx
<polygon
  points={`${-headSize / 3},${-headSize / 2} ${headSize * 2 / 3},0 ${-headSize / 3},${headSize / 2}`}
  fill="transparent"
  stroke={strokeColor}
  strokeWidth={Math.max(2, obj.strokeWidth || 2)}
  strokeLinejoin="round"
  transform={`translate(${tipX},${tipY}) rotate(${angleDeg})`}
/>
```

**Stroke width:** `max(2, obj.strokeWidth || 2)` — legacy `createArrowhead` OPEN_TRIANGLE branch (`PageAnnotationLayer.jsx:430`).

**Line-shortening (straight arrow):** Apply the same `headSize / 3` shortening as SOLID_TRIANGLE — prevents stroke bleed-through at the tip apex.

---

#### C.6 — `HORIZONTAL_LINE` (`'horizontalLine'`)

**Visual:** A perpendicular tick crossing the line axis at the tip. Reads as a "stop" or "measurement end" marker.

**Local-frame geometry:**

- Half-length: `halfLength = headSize / 2`
- Line from `(0, -halfLength)` to `(0, +halfLength)` — perpendicular to the arrow axis (arrow direction is +x in local frame; the tick lies along the y-axis)

**SVG output:**
```jsx
<line
  x1={0} y1={-headSize / 2}
  x2={0} y2={+headSize / 2}
  stroke={strokeColor}
  strokeWidth={Math.max(2, obj.strokeWidth || 2)}
  strokeLinecap="round"
  transform={`translate(${tipX},${tipY}) rotate(${angleDeg})`}
/>
```

**Stroke width:** `max(2, obj.strokeWidth || 2)` — legacy `createArrowhead` HORIZONTAL_LINE branch (`PageAnnotationLayer.jsx:449`).

**Line-shortening:** NONE — the tick crosses the line axis flush at the endpoint.

### Section D — Head-Size Formula Reconciliation (IMPORTANT)

**Decision locked here:** Phase 15's `renderArrowhead` uses `headSize = max(8, strokeWidth × 3)`, **matching the existing `svgAnnotationRenderers.jsx:163` formula**, NOT the legacy `createArrowhead` formula of `max(12, strokeWidth × 3)` at `PageAnnotationLayer.jsx:349`.

Rationale:

1. Pre-Phase-15 arrows (all `SOLID_TRIANGLE`) currently render via `svgAnnotationRenderers.jsx:163-181` with `max(8, sw × 3)`. Switching the whole system to `max(12, sw × 3)` would grow existing arrow heads on reload.
2. The no-regression screenshot contract in 15-CONTEXT.md Area 4 explicitly mandates that straight lines/arrows render identically before and after Phase 15. Changing the min from 8 → 12 would fail that contract.
3. The legacy PAL formula is a **Fabric.js coordinate formula** for a Fabric `Triangle` object's bounding-box-driven sizing — its semantics are different from SVG polygon-point geometry. Lifting the formula without its context would be a bug.

**Implication for all 6 styles:** When the styles reference `headSize`, they mean `max(8, strokeWidth × 3)`. The `max(2, strokeWidth)` stroke-width clamp on the 5 non-SOLID_TRIANGLE styles is preserved from legacy — different axis, different purpose (stroke visibility minimum, not geometry minimum).

**Floor behavior:** At `strokeWidth=1` the effective arrowhead size is `max(8, 3) = 8`. At `strokeWidth=4` it's `max(8, 12) = 12`. At `strokeWidth=10` it's `max(8, 30) = 30`. Linear scaling above stroke width ≈ 2.67.

### Section E — Interaction Contract (Midpoint Drag)

| Stage | Trigger | Behavior | Visual feedback |
|-------|---------|----------|-----------------|
| Idle (selected, straight) | n/a | Midpoint handle renders at geometric midpoint; cursor `grab` on hover | 3 handles visible: p1, midpoint (smaller), p2 |
| PointerDown on midpoint handle | `pointerdown` on circle | `handleHandlePointerDown(e, 'midpoint')` dispatches; `dragStateRef.current = { active: true, mode: 'midpoint', ... }` | Cursor becomes `grabbing` |
| PointerMove during drag (inside 10px of baseline) | `pointermove` | **LINE STAYS STRAIGHT** — `data.midpoint` is NOT written because `shouldSnapToLinear` would immediately clear it. Alternative: write midpoint but let renderer's 1px hysteresis hide the near-zero curve. Planner's call; either path produces the same visible output. | Line stays straight, midpoint handle tracks pointer |
| PointerMove during drag (outside 10px of baseline) | `pointermove` | `data.midpoint = { x: pointerX, y: pointerY }` written live with `checkpointPolicy: 'skip'`. Renderer re-enters `<path>` branch. | Curve visibly passes through pointer (`t=0.5`). No color change, no snap indicator, no animation. |
| PointerUp (midpoint outside 10px) | `pointerup` | Final commit with `checkpointPolicy: 'normal'` (adds to undo stack). | Curve locks in, cursor returns to `grab` |
| PointerUp (midpoint within 10px) | `pointerup` | `shouldSnapToLinear === true` → clear `data.midpoint`. Single `checkpointPolicy: 'normal'` commit. | Line snaps straight; midpoint handle re-positions to new geometric midpoint. **SILENT** — no animation, no flash, no sound. |

**Snap feel rule (LOCKED):** The user must not be able to tell whether the 10px threshold is being approached during a drag. No handle color change. No ring pulse. No "sticky" animation as the pointer enters the snap zone. The line going straight at release IS the feedback. This is a deliberate match to combined-tools' behavior.

**Endpoint-drag-preserves-midpoint (LINE-03 / ARROW-03):**

| Stage | Behavior |
|-------|----------|
| PointerDown on p1 or p2 | Existing endpoint drag mode; if `data.midpoint` is set, capture it into `dragStateRef.current.originalMidpoint` for the drag lifetime. |
| PointerMove | `data.midpoint` stays at its original absolute page coords. Renderer re-draws the curve with new `(x1,y1)` or `(x2,y2)` but the midpoint unchanged. |
| PointerUp | Run `shouldSnapToLinear(midpoint, newStart, newEnd)` — if true, clear `data.midpoint` and restore straightness with geometric midpoint. If false, commit with midpoint preserved. |

**No new visual indicator** for the auto-revert on collinearity — it's silent, same as midpoint-drag snap.

### Section F — Selection Outline / Bounding Box (curved lines)

Curved lines have a non-rectangular geometry that bulges away from the straight baseline. The selection outline today (for line-type annotations at `SVGAnnotationLayer.jsx:1763-1806`) renders **only the 2 endpoint handles** — no dashed bbox rectangle for line-type annotations.

**Phase 15 extends this with the 3rd midpoint handle but preserves the "no bbox rectangle" rule.** Do NOT add a dashed bounding-box rectangle around curved lines. The three handles (p1, midpoint, p2) are sufficient visual indication of selection.

**Hit-testing bbox (non-visual, for click-to-select):** The planner's discretion call — analytical bbox from start/end/midpoint/control-point is preferred over `<path>.getBBox()` for determinism pre-mount. This is a code decision, not a visual contract — invisible to the user.

## Accessibility Notes

Phase 15 introduces three interaction surfaces. A11y treatment:

| Surface | A11y approach |
|---------|----------------|
| Midpoint handle (keyboard) | **Not keyboard-accessible in Phase 15.** Consistent with existing p1/p2 endpoint handles (pointer-only). A keyboard-accessible curvature adjustment would use the Phase 16 typeable curvature pill (`RotationInputField` pattern, keyboard-first). |
| Midpoint handle (screen reader) | `<title>Drag to bend</title>` child of the `<circle>` is the minimum affordance. Optional per §Copywriting. |
| Curved line rendering | SVG `<path>` inherits the same a11y posture as the `<line>` branch (i.e., none beyond visible geometry). Phase 15 does not regress. |
| Arrowhead styles | Pure decoration — no a11y role. Their meaning is encoded in the annotation type, which Phase 16's picker UI will label. |

**Color contrast:** The `#4a90e2` blue handle ring on white fill gives ~3.8:1 contrast with the PDF's typical white page surface — meets WCAG AA for non-text graphical objects (3:1). Drop-shadow reinforces the edge.

## Issue 1 — Caret drifts vertically as text wraps

**Symptom (user words):** "Horizontally the caret stays ahead of each
letter correctly. Vertically, the more I type and the more it wraps, the
farther and farther away the cursor gets from the text."

**Hypothesis (user confirmed alignment):** Two separate line-height
rulers. Fabric's Canvas 2D text metrics compute line spacing one way
(uses `fontSize * lineHeight * _fontSizeMult`), the SVG `<foreignObject>`
CSS `lineHeight` uses the browser's own line-box algorithm. On line 1
they agree; each subsequent wrapped line the caret moves down by Fabric's
step, the visible letters move down by the browser's step, and they drift
apart.

**Evidence needed before fix:** user specifically asked for diagnostic
logs to confirm the hypothesis before coding a fix. Plant logs to capture:
- Fabric's `textObj._textLines.length`, `textObj.lineHeight`,
  `textObj._fontSizeMult`, `textObj.fontSize`
- Fabric's computed caret screen position (hiddenTextarea rect OR
  `getCursorBoundaries()` return)
- SVG `<foreignObject>` text box rect
- Browser-resolved line-height on the inner `<div>` (getComputedStyle)
- Per-line `getBoundingClientRect` of `<foreignObject>` children OR
  measure rendered line positions in the SVG

Hook the logs into the existing `textObj.on('changed')` callback at
`FabricEditCanvas.jsx:~1592`. User will hand back one log, expect yes/no
on the hypothesis. MAX depth per the "diagnostic logs must be maximally
in-depth" feedback memory — don't emit 3 rounds of logs to extract one
answer.

**Likely fix (after confirmation):** force the SVG's inner `<div>`
`lineHeight` CSS to match Fabric's math exactly:
```js
lineHeight: `${obj.lineHeight * obj._fontSizeMult || 1.16}`
```
Or flip to Option 2 (tspan lines with per-line `dy = lineHeight *
fontSize` in SVG units) — the caret then lives in the same coordinate
space as the rendered lines.

## Issue 2 — New-creation shows Fabric, not SVG

**Symptom (user words):** "When I first created the text box, it looks
like it's showing the fabric.js rather than first showing the SVG. When
I go into imported text boxes, I never see fabric.js. Shapes are doing
the same thing — when I first create the shape, I see the fabric JS
shape being created, and then once I commit it, it changes to SVG and I
can visibly see that."

**Root cause:** The new-text creation path at
`FabricEditCanvas.jsx:~1372-1402` sets `fill: strokeColor` +
`stroke: '#000000'` (opaque) because there's no SVG annotation yet for
Fabric to sit invisibly under. Same for shape creation (presumably in
`FabricDrawingCanvas.jsx` or a creation-tool surface).

**Fix approach (no logs needed — structural):**
1. During creation, mount a **preview SVG annotation** that renders from
   the in-flight Fabric state (same liveTextEditBounds bridge, but
   seeded from create-drag state).
2. Make Fabric's new-text textbox transparent (fill + stroke
   `rgba(0,0,0,0)`) same as existing-text path.
3. On commit, the preview becomes the real annotation. No visible swap.

**Files expected to touch:**
- `src/components/FabricEditCanvas.jsx` — new-text branch's fill/stroke.
- `src/App.jsx` — new creation-preview state + feed it into
  SVGAnnotationLayer as an extra ephemeral annotation OR extend
  liveTextEditBounds to carry a "create mode" flag.
- `src/components/SVGAnnotationLayer.jsx` — render the preview.
- For SHAPES: same pattern in the shape-create path
  (FabricDrawingCanvas.jsx shape-creation tools, currently mounting
  Fabric as the only visible layer during drag).

**Watch-out:** Shape creation uses `FabricDrawingCanvas` which has a
different lifecycle than `FabricEditCanvas`. May need a separate bridge
or a shared "in-flight annotation preview" mechanism that both feed.
Worth scoping before coding.

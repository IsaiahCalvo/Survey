## What landed this session (2026-05-03)

Six fixes shipped in sequence after the user opened a real production doc
(Package 2 - Rev 4 -- IC.pdf, document_id `70dadd86-35f0-432b-925f-c59e919a4e4d`,
22,630 non-highlight legacy rows) and exposed the original phase 31 cutover
seal as broken:

1. **`fix(31): paginate backfill SELECT so PostgREST 1000-row cap stops sealing on truncated input`** (commit `0963a2dd`).
   Root cause: `supabase.from('document_annotations').select('*')` was not
   paginated. Supabase / PostgREST applies `max_rows = 1000` server-side
   (confirmed by `supabase/config.toml:18`). The bare SELECT silently
   truncated to first 1000 rows; the verified-count gate
   (`yMapSize >= imported`) was satisfied with 1065 ≥ 1000 (the 65 being
   mid-flight collaborator writes) and the seal landed on a partial Y.Map.
   Fix: `BACKFILL_PAGE_SIZE = 1000` + `.range(from, to)` loop matching
   `annotationCloudSync.loadPagedAnnotationRows` shape. New regression
   test `crdtBackfill #7` locks the >1000-row case (2,500-row fixture →
   3 `.range()` calls → yMap.size === 2500). Test mock chain extended.

2. **`fix(31): gate window-focus rehydrate on cutover_completed_at`** (commit `9519f602`).
   Root cause: the window `focus` listener in `useAnnotationCloudSync.js`
   `onFocus` ran `loadCloudWithEmptyVerify` unconditionally → 30s legacy
   load → `setAnnotationsByPage(focusFresh)` REPLACED the Y.Doc-materialized
   state with stale legacy data, wiping CRDT-only writes (the captured
   counter pin in the 15:20:12 regression). Fix: cache cutoverTs in
   `cutoverTsRef.current` from the hydrate effect; in `onFocus`, early-
   return when `cutoverTsRef.current && phase30Ydoc` — sealed-doc focus
   trusts Y.Doc + realtime as source of truth.

3. **`fix(31): unseal Package 2 after backfill-truncation hotfix`** (commit `8df5a874`).
   Migration `20260503154950_phase31_hotfix_unseal_truncated_doc.sql`
   resets `cutover_completed_at = NULL` on the captured doc so the
   next open re-runs the now-paginated backfill. Applied to live Survey
   project via `supabase db push --linked --include-all` 2026-05-03 ~15:50 PT.

4. **`fix(31): re-run import loop when markCutoverComplete is requested even if doneKey is set`** (commit `9ee8b1bb`)
   + **`fix(31): re-unseal Package 2 after recovery-path fix landed`** (migration `20260503160212`, commit `2abe81ab`).
   Discovered: even with the doc unsealed, the per-user `backfill_done` Y.Map.meta
   marker still triggered the doneKey short-circuit, sealing the same
   incomplete Y.Map without re-importing. Fix: when `markCutoverComplete`
   is requested, fall through past the doneKey check regardless of marker
   state. Bridge idempotency makes re-runs cheap on already-imported rows.

5. **`fix(31): order paginated backfill SELECT by page_number to match working legacy reader`** (commit `0c4890df`).
   16:42:30 UAT log: paginated SELECT page 0 (range 0-999) timed out at
   9,982 ms with Postgres `57014 statement_timeout`. Root cause: my
   `order('created_at') + order('highlight_id')` forced a full sort over
   the full 22,630-row span on every page request — no covering index
   for that ordering. The legacy reader uses
   `order('page_number', { ascending: true })` which follows the natural
   `(document_id, page_number)` index ordering and completes the same
   22-page scan in ~30s without timing out. Switched the backfill to the
   same ordering. Backfill creation-order preservation was a soft preference
   for activity-log readback; bridge idempotency makes any stable ordering
   correctness-preserving across re-runs (the gate's `yMapSize >= imported`
   is order-independent).

6. **`chore(31): bulletproof Cmd+Shift+L + per-page hydrate breakdown`** (commit `4cd24310`).
   User requirement: "Cmd+Shift+L should always just be a natural hotkey
   to save the logs, both locally and to GitHub — no matter what state
   the app is in (home page, settings, template project, PDF view, survey
   mode, post-error)." Fix: added a capture-phase keydown listener at
   module-init in `src/main.jsx` (BEFORE React mounts). Lives outside
   the React tree so it survives any error-boundary fallback, route
   change, App-level useEffect detach, or component crash. Wrapped every
   step in try/catch so a missing electron bridge or downstream throw
   never prevents the next step. Also exposed `window.__networkLogSnapshot`
   from `networkLogger.js` for the import-free probe path. Existing
   in-App listener kept as the GitHub-push driver via the dispatched
   `save-log-banner-start` event.

7. **`fix(31): probe Y.Map vs legacy count before trusting cutover-already-complete short-circuit`** (commit `ed3488cc`).
   18:13:34 log captured: doc was sealed at cutoverTs `2026-05-03T16:46:01.324`
   but Y.Doc had only 3 entries materialized while the legacy table still
   had 3,058 fabric rows across 6 pages. Root cause: local IndexedDB Y.Doc
   cache lost data between sessions (browser quota, dev-server restart,
   y-indexeddb chunk corruption, machine switch — all plausible). The seal
   contract assumed Y.Map is always in sync with imports. It isn't. Fix:
   before the `cutover_already_complete` short-circuit fires, run a HEAD
   count probe against legacy and compare with Y.Map.size. If Y.Map is
   within 5% (or 100 rows absolute, whichever larger) of legacy, trust
   the seal. If suspiciously small, fall through to the paginated import
   loop and top up Y.Map. Seal stays as-is; bridge idempotency makes the
   re-run cheap.

8. **`fix(31): hydrate-time degeneracy guard so legacy data stays visible while backfill recovers`** (commit `414deff7`).
   18:35:57 log captured: degeneracy probe correctly detected 3-vs-22,630
   mismatch and re-ran the import (yMapSizeAfter:22,631), but the user
   STILL saw missing annotations because the cutover hydrate had already
   clobbered React state (3,059 → 3) BEFORE the backfill effect could
   repair Y.Map. Hydrate fired first; backfill fired second; state stuck
   at 3 even after Y.Map was repaired. Fix: gate the state replacement
   in the cutover-sealed hydrate. If the Y.Map snapshot has materially
   fewer entries than current state (<80% when state >= 10), skip the
   replacement and trust current state until the backfill repairs Y.Map
   in the background. On the NEXT open, Y.Map is healthy, the guard is
   a no-op, and hydrate replaces state cleanly. Threshold tuned so
   initial-mount hydrate (state empty, Y.Map healthy) still works.

## Open issue — wake up here

User just reported (post-414deff7): "the imported annoations seem to be
coming in but the native in-app anotaitons are not."

Latest log `Logs/2026-05-03_18-42-03/console.log` shows:
- cutover-sealed hydrate at line 54: `yMapSize:21627, materializedTotal:21627,
  materializedDrawnByMe:0, materializedDrawnByOthers:21627, materializedImported:0,
  pages:7, perPage:{"1":1,"6":1642,"7":988,"8":3144,"9":12160,"10":2640,"11":1052}`
- legacy load: `rowsByType:{"ink":22584,"square":42,"freetext":4,"highlight":1820}`
- Backfill recovery loop in flight (still in progress at snapshot time):
  page 21 of ~23, totalSoFar:22000.

### What I think is happening

`materializedDrawnByMe:0` is misleading — the breakdown helper
(`__phase31UatBreakdown` in `src/hooks/useAnnotationCloudSync.js`) only
inspects `obj.data.userId / authorId / authorId`. The bridge writes
`meta.authorId` in the Y.Map's `meta` sub-map (per
`crdtAnnotationBridge.applyFabricCreate`), which is NOT in the materialized
fabricObjects. So every materialized entry shows as "not me". Helper bug,
not data bug.

### What might still be a real problem

Y.Map size 21,627 vs legacy 22,630 = **1,003 entries missing from Y.Map**.
Roughly close to 1,003 of 22,630 legacy non-highlight rows (4.4% gap).
The user's "native in-app annotations" lane includes 42 squares + 4 freetext
+ counters + callouts. Counters are stored as `annotation_type='counter'`
in document_annotations but the legacy `rowsByType` shows zero counter rows.
Either (a) the user has zero counter annotations on Package 2 (plausible —
they only just placed one for the test), or (b) counters live on a different
storage path entirely.

  Pre-existing, not caused by Phase 31. Probably should be retired now

## Root cause analysis (confirmed, do not re-investigate)

**Drag-rotate (instant):** SVG paints via `<g transform="rotate(deltaAngle, cx, cy)">` wrapper driven by `visualTransform.rotate`, which is set synchronously inside `handlePointerMove` on every tick. The heavy `onSaveAnnotations` fires only on `pointerup` — by then the user has already seen the final frame.

**Enter/Arrow commit (laggy):** `handleRotationInputCommit` calls `onSaveAnnotations` directly. That routes through `App.jsx:22796 handleSaveAnnotations` which runs, in order on the main thread:
1. `normalizeCanvasJsonForHistory(currentPageAnnotations)` — walks the full annotations object
2. `normalizeCanvasJsonForHistory(json)` — walks it again
3. `getHistoryFingerprint(prev)` + `getHistoryFingerprint(next)` — hashes serialized copies
4. `summarizeAnnotationPageTransitionForDebug(...)` — diffs objects field-by-field
5. `pushHistoryDebugEvent('annotations_save_detected', ...)` — dispatches debug event
6. `addHistoryCheckpoint('annotations:save', ...)` — pushes undo entry
7. `setAnnotationsByPage(prev => { JSON.stringify deep-compare; ... })` — another deep compare inside the reducer
8. `renumberCounters(next)` — walks all counters across all pages
9. React reconciles and re-renders all visible SVGAnnotationLayer children

Items 1-8 run synchronously before React even starts the re-render. On a document with many annotations this is easily a multi-frame budget overrun — the visible shape stays at its old angle for a perceptible beat. Drag-rotate avoids this because `visualTransform.rotate` paints instantly via SVG transform and the heavy pipeline runs only on drag-end when the user isn't watching for micro-latency.

**The investigation candidates from the gap source, ruled out:**
1. `setTimeout` wrapping `onCommit` — NONE exists in RotationInputField.jsx (verified by grep).
2. `normalizeTypedDegrees` expensive — it's a pure ~10-line string-to-int helper; not it.
3. Intermediate `setInputValue` → `setTimeout(onCommit, 0)` — NONE exists; `commitTyped` calls `onCommit` directly at line 413.
4. `useSVGInteraction` re-running the rotate branch after typed commit — the rotate branch only runs during an active `pointermove` with `ds.active = true`; typed commits don't trigger it.
5. Shift+Arrow ±45° vs single Arrow ±1° taking different paths — they DON'T. Both go through the same `onCommitRef.current?.(annotationIndexRef.current, next)` at line 362. The reason Shift+Arrow ±45° feels "pass" in UAT Test 10 while ±1° feels laggy in Test 9 is that a 45° jump is visually dramatic enough that users subjectively accept it; a 1° jump is subtle and the frame lag becomes the dominant signal. Both paths have the same underlying lag — Test 10 just masks it.

**Why this fix is surgical:** The fix mirrors the proven drag-rotate pattern by exposing a single `applyOptimisticRotation` helper on the hook. The commit handler calls it first (cheap visual paint), then calls `onSaveAnnotations` (heavy pipeline, runs on subsequent frames). A cleanup `useEffect` clears the optimistic transform once the persisted annotation catches up. Total: ~30-60 LOC across two files, no new files, no touched protected files, no changes to RotationInputField.jsx or its diagnostic scaffolding.

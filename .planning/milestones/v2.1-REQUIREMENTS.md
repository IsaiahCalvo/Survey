## v2.1 Requirements (Stage 0: Shape Edit Polish)

Requirements for Phase 12 — Shape Edit Polish. Continues EDIT and ZOOM
category numbering from v2.0.

### Canvas Editing

- [x] **EDIT-11**: User can hold Shift during SVG shape rotation to
      soft-snap the rotation angle to the nearest 45° increment
      (0°/45°/90°/135°/180°/225°/270°/315°) when the free angle is within
      3° of the increment. Outside the 3° threshold, rotation remains free
      even while Shift is held (so Shift-at-23° stays at 23°, Shift-at-43°
      snaps to 45°, Shift-at-41° stays at 41°). Releasing Shift always
      returns to free rotation. Applies to the SVG interaction path only;
      Fabric edit canvas shape rotation is commit-lossy and out of scope.

      **Outcome:** ✅ Validated. Shipped in Plan 12-01 at commit
      `df43b0f8` (wire) + commit `9b0c6f1c` (helper). Evidence:
      - `src/utils/svgTransformMath.js:121-127` — `snapAngleToNearest45`
        pure helper with `% 360` defensive wrap
      - `src/hooks/useSVGInteraction.js:456-461` — `let newAngle` promotion
        + Shift-guard + snap call in rotate branch
      - `tests/svgTransformMath.test.mjs` — 10/10 cases green (44→45, 41
        free, 23 free, 358→0 wrap, exact 0/45/135, 317→315)

- [x] **EDIT-12**: When a shape is selected and a rotation drag is active
      (or when hovering the rotation handle), the user sees an inline
      numeric input field near the rotation handle displaying the current
      rotation angle in degrees. The user can type an exact value, commit
      with Enter or blur to apply the rotation, or cancel with Escape.
      Input values are normalized to `[0, 360)` and applied atomically to
      the annotation angle. Positioning tracks the handle during rotation
      and remains on-screen at zoom ≥ 25%.

      **Outcome:** ✅ Delivered with 2 open polish gaps. Shipped across
      Plans 12-02 (component) and 12-03 (gap closure for commit latency).
      Evidence:
      - `src/utils/rotationInputHelpers.js` — 184 LOC pure helpers
        (`normalizeTypedDegrees` + `computeInputPosition` with
        constant-radius extension)
      - `src/components/RotationInputField.jsx` — 646 LOC HTML portal
        component (createPortal, uncontrolled input, hover-intent + drag-wins
        visibility state machine, Enter/Escape/blur/Arrow semantics)
      - `src/components/SVGSelectionOverlay.jsx:168` — `data-rotation-handle="mtr"`
        attribute for getBoundingClientRect lookup
      - `src/components/SVGAnnotationLayer.jsx:132,365-439,1299-1309` —
        parent wiring + optimistic-paint cleanup useEffect
      - `src/hooks/useSVGInteraction.js:835-855` — `applyOptimisticRotation`
        helper (Plan 12-03)
      - `src/hooks/useSVGInteraction.js:861-863` — `clearOptimisticRotation`
      - `tests/rotationInputHelpers.test.mjs` — 34/34 cases green

      **Open polish gaps (deferred to v2.2+):**
      - **Gap 3** — Rotation pill doesn't reappear on hover after returning
        from edit mode via click-off; full deselect + reselect is the
        workaround. Suspect: stale `handleEl` ref in `SVGAnnotationLayer.jsx`
        hover-intent effect dep array after React reconciles the overlay.
        Filed in `.planning/FEATURE-BACKLOG.md` Stage 0.
      - **Gap 4** — Rotation handle (mtr) clipped when a pre-rotated shape
        enters edit mode (doesn't reproduce at 0°). Suspect: `FabricEditCanvas`
        container `overflow: hidden` / clip-path. Filed in
        `.planning/FEATURE-BACKLOG.md` Stage 0.

      **De-scoped (user decision during 12-02 UAT):**
      - **AC #7 blur-commit of typed value** and **AC #8 invalid-value revert**
        — user explicitly declined: "no but thats fine, i dont want that."
        The pill currently commits on Enter and reverts on Escape; blur is
        treated as "no change." Documented in `12-02-SUMMARY.md`.

### Zoom & Integration

- [x] **ZOOM-09**: User can zoom the PDF down to 10% via every zoom entry
      point (toolbar buttons, keyboard shortcuts, scroll wheel, zoom input
      box, fit-to-page/fit-to-width) without the app silently re-clamping
      the floor to a higher value.

      **Outcome:** ✅ Validated. Shipped in Plan 12-01 as atomic 2-file
      commit `df43b0f8`. Evidence:
      - `src/utils/zoomController.js:15` — `MIN_SCALE: 0.5 → 0.1`
      - `src/App.jsx` (commitZoomInput pre-clamp) — `Math.max(parsed, 50)`
        → `Math.max(parsed, 10)` in the SAME commit
      - `tests/zoomController.test.mjs` — 7/7 boundary tests green (0.1
        floor, 0.05→0.1 clamp, 0.5 untouched, 5.0 ceiling, 6.0→5.0 clamp,
        NaN→1.0 fallback, string→1.0 fallback)

      **Accepted table-stakes behavior:** At zoom levels below 25% the
      selection/rotation handles remain visible but become hard to target.
      Matches Illustrator/Photoshop convention — the user is expected to
      zoom back in to edit and no defect is recorded.

## Changes from Original Scope

### Plan 12-01 scope expansion — 9 gap bugs folded in

Original scope: 3 tasks (Wave 0 helper + tests, Wave 1 ZOOM-09 atomic, Wave
1 EDIT-11 wire) for a ~8-LOC net change. Expanded in-flight to include 9
gap bugs discovered during human verification:

- Bug #1 — live-update zoom input during deferred setScale path
- Bug #1b — reconcile React zoom state from live DOM at load
- Bugs #2 / #2.5 / #2.5v2 — fit-height from live Syncfusion container,
  rewired to `zoomTo()` directly, skipping pdf.js re-fit in Syncfusion mode
- Bug #2.6 — fit-page uses pdf.js `pageSize` × calibrated Electron device
  factor (the Syncfusion-reported zoom percentage is unreliable under
  Electron's 1.33 factor)
- Bug #3 — blue-glow removal, line/arrow stroke visibility, handle
  dampening across SVGAnnotationLayer + SVGSelectionOverlay + svgAnnotationRenderers
- Bug #4 — shape edit handle clip + constant offset in FabricEditCanvas
- Bug #5 — rect/circle edit-mode scale desync + circle first-time jump
- Bugs #6/#7 — edit-mode transform parity + `uniformScaling` + canvas clip
  + mini-bar live vertical tracking with UX comments
- Bug #8 — SVG select-mode flip (rect/circle/ellipse only) via signed
  scale + per-handle direction detection + top-left normalization
- Bug #9 — mini-bar horizontal live-tracking (mirror of Bug #6) with the
  "DO NOT clamp at zero" invariant documented inline

None of these are new v2.1 requirements — they are pre-existing defects in
the dual-path SVG↔Fabric edit model that were fixed to land a coherent
shape-edit experience within the same milestone.

### Plan 12-03 — unplanned gap-closure plan

Plan 12-03 was NOT in the original phase roadmap. It was authored mid-phase
after Plan 12-02's UAT surfaced Gap 1 (Enter-commit and Arrow-nudge lag in
RotationInputField). Without 12-03, EDIT-12 would have shipped broken on
the most common user path (Enter to commit a typed angle).

The fix reused the drag-rotate optimistic-paint pattern: paint
`visualTransform.rotate` first, then dispatch `onSaveAnnotations`. Helper
is `applyOptimisticRotation(idx, newAngle)` at `useSVGInteraction.js:835-855`.
User confirmed "100% approved" on UAT re-run Tests 6 and 9.

### EDIT-12 LOC overage

Original backlog estimate for "Shift+rotate snaps" + "zoom floor at 10%"
combined was ~11 LOC. Actual EDIT-12 shipped:

- `RotationInputField.jsx` — 646 LOC
- `rotationInputHelpers.js` — 184 LOC
- `tests/rotationInputHelpers.test.mjs` — 365 LOC
- `SVGAnnotationLayer.jsx` wiring — ~72 LOC
- `useSVGInteraction.js` optimistic-paint helpers — ~75 LOC

Total EDIT-12 surface: ~1,342 LOC. This was explicitly flagged in STATE.md
decisions as "a scope expansion" once the user confirmed they wanted exact
typed angles, not just Shift-snap. Approved during `/gsd:discuss-phase`.

3. **Handle alignment diagnosis + fix (DONE, user confirmed working):**
   - Root cause: Fabric.js includes `strokeWidth` in bounding rect for controls — BR handle drifts by `strokeWidth * zoom` pixels. TL always correct because Fabric doesn't shift left/top for stroke.
   - Fix: Set `strokeWidth: 0` on invisible Fabric object (SVG is visual truth). Real value stored in `obj._realStrokeWidth`. MiniToolbar reads/writes `_realStrokeWidth`. `commitAndClose` restores it to serialized JSON.

4. **MiniToolbar centering fix (DONE):**
   - Changed from left-aligned to centered: `left = containerRect.left + (containerRect.width - toolbarWidth) / 2`.

5. **MiniToolbar pan-tracking (DONE but introduced new bug):**
   - Added `requestAnimationFrame` loop in MiniToolbar to track container position continuously via `toolbarPos` state. Replaced one-time `getBoundingClientRect()`.

6. **Pan lock (code landed, NOT YET CONFIRMED):**

   - Intent: prevent Fabric from interpreting pan drags as object movement.

7. **Zoom button click-outside exclusion (code landed, NOT YET CONFIRMED):**

<decisions_made>
- Handle alignment: zeroing Fabric strokeWidth on invisible shape object is the correct approach — SVG is the visual truth, Fabric only provides hit zone + handles.
- MiniToolbar tracking: rAF position polling chosen over IntersectionObserver or absolute positioning because toolbar is portaled to document.body with position:fixed.
- Click-outside exclusion uses CSS class selectors (.e-toolbar, .e-pv-nav-bar) rather than checking specific button IDs — more robust against Syncfusion version changes.
- lockMovementX/Y chosen over disabling selectability because handles must remain interactive for resize.

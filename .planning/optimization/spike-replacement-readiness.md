# Spike Replacement-Readiness Audit — `src/prototype/` vs Production PDF Viewer

**Date:** 2026-07-09
**Scope:** Can `?spike=features` (`src/prototype/FeatureSpike.jsx` + `PdfjsArm.jsx` + `InteractiveOverlay.jsx` + `SpikeTextLayer/SpikeLinkLayer/SpikeFormLayer`) replace production's PDF page + annotation renderer stack (`src/components/PdfjsViewerContainer.jsx`, `src/PDFViewer.jsx`, `src/components/SVGAnnotationLayer.jsx`, `FabricDrawingCanvas/FabricEraserCanvas/FabricEditCanvas.jsx`)?
**Method:** Full read of every file in `src/prototype/` (2,589 lines); two parallel code-research passes over the production stack (renderer/zoom/eraser and export/undo/collab, with file:line citations); live browser testing on both routes via Playwright against three real fixtures (36pg package, 99pg SE-011 markups, 120pg synthetic virtualization fixture) plus the perf-gate stress spike at max density.

**Important context the audit vectors assumed differently than reality:** `src/prototype/NOTES.md` records that this spike already answered its original question — "own the renderer on pdf.js vs adopt EmbedPDF" — and the verdict landed on **pdf.js**. Production's `PdfjsViewerContainer.jsx` **is the shipped result of that decision**; it is not a legacy renderer being defended against a newer challenger, it's the production-hardened descendant of the same "Arm A" code path this spike explores. `FeatureSpike.jsx` (`?spike=features`) is a *later, narrower* spike that reuses `PdfjsArm.jsx` to prototype specific missing features (bookmarks, search, links, forms) in isolation, explicitly labeled "THROWAWAY" in its own header comment. This reframes the real question: not "which renderer wins" but "does this narrow feature-prototype's annotation/interaction layer contain enough of production's feature set to justify swapping it in." It does not.

---

## Verdict

### **(3) Not a viable replacement — with a caveat.**

The core pdf.js *rendering* engine underneath the spike (virtualization, cursor-anchored zoom, tiling, race-condition guards) is essentially the same lineage as production's and performs comparably in this audit's tests. But `InteractiveOverlay.jsx` — the spike's *entire* annotation layer — has **zero** eraser, **zero** undo/redo, **zero** collaboration, and **zero** PDF write-back/export. These aren't missing polish; they are core product features (partial-erase ink editing, undo, live collab, and the ability to save a marked-up PDF back to disk) that exist today in production as real, tested, working systems. Replacing production's annotation stack with the spike's would be a regression on every annotation-lifecycle axis except raw select/move/delete.

If the question is narrowed to "should production's *page rendering* (canvas raster, virtualization, cursor-zoom) be modeled after this spike" — it already is; no action needed, they're siblings. If the question is "should `InteractiveOverlay` replace `SVGAnnotationLayer` + the three Fabric canvases" — no, not without first building eraser, undo/redo, collab, and export from scratch inside it, which is most of what production's annotation stack already provides.

## Severity-Prioritized Findings

### BLOCKER — No PDF write-back / export path in the spike
**Severity:** Blocker (per explicit user directive: a missing export/write-back layer is an immediate production blocker)
**File:** `src/prototype/InteractiveOverlay.jsx`, `src/prototype/PdfjsArm.jsx`, `src/prototype/FeatureSpike.jsx` — exhaustively grepped for `save|export|flatten|write-back|pdfAnnotationsPdfLib|saveAsBlob|download` across all of `src/prototype/`; the only hits are `spikeLogger.js`'s perf-log downloader (`RendererSpike.jsx:163-171`, `PerfGateSpike.jsx:152-160`) — unrelated to PDF content.
**Repro:** `extractInkAnnotations()` (`InteractiveOverlay.jsx:69-223`) reads a PDF's real annotation dicts via `pdf-lib` and converts them to editable SVG path objects. There is no inverse function anywhere in `src/prototype/` that takes an edited/added annotation and writes it back into `/Annots`, no `PDFDocument.save()` call, no flatten-for-print path. Deleting a mark (`Delete`/`Backspace`, `InteractiveOverlay.jsx:269-280`) only mutates in-memory React state (`onChange`) — there is no way to persist the result as a PDF.
**Contrast:** Production has two full, independently tested write-back pipelines — `src/utils/pdfAnnotationsPdfLib.js` (`savePDFWithAnnotationsPdfLib`, line 1397; wired to the "Export annotated PDF" toolbar button via `handleExportAnnotatedPDF`, `PDFViewer.jsx:19180/19213`) and a newer flag-gated `src/utils/pdfNativeExport/` adapter pipeline (`bakeAnnotationsIntoPdf`, `index.js:78`), plus a separate flatten-for-print path (`savePDFWithFlattenedRegularAnnotationsForPrint`, `pdfAnnotationsPdfLib.js:1328`). Both are round-trip tested (`tests/pdfSaveExportContract.test.mjs`, `tests/pdfNativeExport.roundTrip.test.mjs` reload the written bytes with `PDFDocument.load` and assert on `/Annots` shape).
**Fix if pursuing replacement:** Port `pdfAnnotationsPdfLib.js`'s per-type creators (`createInkAnnotation`, `createSquareAnnotation`, etc.) or the newer `pdfNativeExport` adapters into the spike before it could touch a real document.

### BLOCKER — No eraser of any kind in the spike
**Severity:** Blocker
**File:** `src/prototype/InteractiveOverlay.jsx` — grepped for `erase|eraser|Eraser` across all of `src/prototype/`: zero matches.
**Repro (browser):** `?spike=features` toolbar has exactly four controls: "Load PDF…", three fixture buttons, "Find." No eraser tool, no eraser button, no eraser cursor mode. The only removal mechanism is whole-object delete via `Delete`/`Backspace` on a selected mark (`InteractiveOverlay.jsx:269-280`) — an all-or-nothing operation, not a partial erase.
**Contrast:** Production's toolbar (verified live, `?testPdf=` route) has a "Draw" submenu exposing "Pen," "Highlighter," "Eraser type," and "Partial erase" as distinct, clickable tools. The math underneath is substantial and specialized: `src/utils/inkEraser.js` (423 lines) implements swept-capsule interval splitting — `erasePathWithCapsules` (`:414-423`) parses SVG path data into typed subpath segments, computes per-segment erased parameter-intervals against each capsule (`segmentCapsuleIntervals`/`segmentCircleInterval`/`segmentRectInterval`, `:69-157`), merges overlaps, and re-splits each subpath into surviving runs. `src/utils/geometryEraser.js` (618 lines) implements a second, boolean-polygon approach (`booleanErasePath`, `:502+`) — building the eraser's swept shape as a union of capsule polygons, then boolean-subtracting it from the stroke's own outline polygon. This is two independently-engineered erase algorithms in production against zero in the spike.

### BLOCKER — No undo/redo in the spike
**Severity:** Blocker
**File:** `src/prototype/*` — grepped for `undo|redo|history|ctrlKey.*z` across all of `src/prototype/`: zero matches.
**Repro (browser):** drew a mark on `?spike=features`, no undo affordance exists anywhere in the UI or keyboard handling; the only "undo" is manually re-selecting and deleting the shape.
**Contrast:** Production's toolbar has working, empirically-verified Undo/Redo buttons. Live test: drew a pen stroke on the 120-page test fixture (`?testPdf=spike-120-pages.pdf`) — page's committed-annotation SVG path count went 1→3; clicked "Undo" — count went back 3→1 and the "Redo" button (previously disabled) became enabled. Source: dual history engine in `PDFViewer.jsx` — local-annotation-history path plus a parallel Yjs `Y.UndoManager` path — `addHistoryCheckpoint` (`:9948`), `handleUndo` (`:10691`), `handleRedo` (`:10883`).

### BLOCKER — No collaboration/sync in the spike
**Severity:** Blocker (confirmed absent, per the audit's own expectation)
**File:** `src/prototype/*` — grepped for `supabase|collab|Yjs|y-webrtc|broadcast|realtime|Realtime`: zero matches. `FeatureSpike.jsx` loads fixtures via plain `fetch()`; there is no multi-user state anywhere in the spike.
**Contrast:** Production has a real CRDT stack — `src/lib/collab/ydocRegistry.js:28` is the app's sole allowed `new Y.Doc(...)` call site, feeding `src/components/collab/YDocProvider.jsx`, `src/lib/collab/SupabaseYjsProvider.js`, and a Supabase Realtime broadcast channel wired at `PDFViewer.jsx:17411-17422` (`supabase.channel(\`yjs:${documentId}\`)`).

### HIGH — Spike's text-selection layer is functionally broken due to a pdf.js API-version mismatch
**Severity:** High
**File:** `src/prototype/SpikeTextLayer.jsx:41` (`el.style.setProperty('--scale-factor', String(scale))`)
**Repro (browser, root-caused):** On `?spike=features` with the real 36-page package, the `.spikeTextLayer` container's `getBoundingClientRect()` reports `width: 0` despite spans being present in the DOM. `document.elementFromPoint()` at the visual center of rendered text returns the underlying `CANVAS`, not a text span — confirming the layer does not actually receive pointer events there. Three independent selection attempts (mouse drag, double-click, triple-click) all returned `window.getSelection().toString() === ''`. **Root cause confirmed empirically**: `pdfjs-dist` is pinned at `^6.1.200` (`package.json`), and that version's bundled `TextLayer.render()` (`node_modules/pdfjs-dist/legacy/build/pdf.mjs:7480-7481`) sizes its container using `width: round(down, var(--total-scale-factor) * Wpx, var(--scale-round-x))` — a CSS custom-property trio (`--total-scale-factor`, `--scale-round-x`, `--scale-round-y`) that `SpikeTextLayer.jsx` never defines (it only sets the older `--scale-factor`, a pre-v5 pdf.js API). Injecting the missing three properties via `page.addStyleTag` immediately fixed it: container width went from `0` to `1192px` (matching the canvas). This is a real, fixable bug, but as shipped, text selection does not work in the spike.
**Caveat on production's equivalent:** production's own `src/components/PdfjsTextLayer.jsx` has the *same* "only sets `--scale-factor`" pattern (line 70) — but it also explicitly sets `el.style.width`/`el.style.height` in pixels immediately before calling `pdfjsLib.TextLayer`'s render, which may or may not survive `TextLayer.render()`'s own inline-style write depending on call order (not independently re-verified against the same live crash, see below). More importantly: this audit could **not** empirically confirm production's text-selection works in this build at all — `PdfjsTextLayer` only mounts when `activeTool === 'text-select'` (`PDFViewer.jsx:28553`), and an exhaustive repo-wide grep found **zero call sites** that ever set `activeTool` to `'text-select'` (checked every `setActiveTool(...)` call site's argument across `src/`, plus `KeyboardShortcutsOverlay.jsx` and `SearchTextPanel.jsx`). Clicking the toolbar's "Select" (pointer) tool did not mount `.pdfjsTextLayer`, and dragging across visible page text with it active produced no selection either. **This is a pre-existing production gap, unrelated to the spike, and out of scope to fix here** — but it means the audit cannot certify "production text selection > spike text selection" from live evidence; it can only certify that neither route demonstrably selects text as currently wired, for two different reasons (spike: rendering bug; production: no UI trigger reaches the code path).

### MEDIUM — "240,000 virtual annotations" is not a number that appears anywhere, and the real achievable count is smaller
**Severity:** Medium (marketing/measurement-precision issue, not a functional bug)
**File:** `src/prototype/PerfGateSpike.jsx:28` (`const DENSITIES = [100, 300, 600, 1000];`), `src/prototype/PdfjsArm.jsx:67-91` (`makeStressShapes`)
**Finding:** Repo-wide grep for `240,000|240000|240k` found **zero** matches related to this claim (the only hit is an unrelated "~240k weekly npm downloads" line in `docs/audits/SYNCFUSION-EMBEDPDF-AUDIT.md`). The actual math: `PerfGateSpike.jsx`'s density knob tops out at **1,000 shapes/page**; its default 120-page fixture (`spike-120-pages.pdf`, page count independently verified via `pdf-lib`: exactly 120 pages) caps the theoretical maximum at **1,000 × 120 = 120,000** synthetic shapes — half of "240,000," not the number itself. Whatever the origin of "240,000" (verbal estimate, doubled count, or a different fixture), it is not a value the current code can produce or that appears in any source file.
**What's actually simulated vs real (verified live in browser):** Turning "Stress overlay ON" at density 1000 and inspecting the DOM directly showed **exactly 1,000 `<svg><path>` elements** — matching one mounted page. Virtualization is real and enforced: across every test in this audit (120-page fixture, multiple scroll positions), only **1–16 pages** were ever simultaneously mounted with a canvas (2 near the top of a scrolled viewport at 100% zoom; 16 when zoomed far out enough that more pages fit the ~1.2-viewport mounting margin — this is a wider window, not a virtualization failure). So the true worst-case simultaneous shape count observed was **16,000 `<path>` elements** (16 mounted pages × 1,000/page), not 120,000 and nowhere near 240,000. The "240,000" framing, if used to describe *live, rendered* annotation load, overstates what's actually in the DOM at any moment by roughly 15–240×, depending on which number was intended. Even at the observed worst case, performance held: a full ctrl+wheel zoom sweep with density-1000 stress active measured p95 frame time of **9.9ms** (well inside a 16.7ms/60fps budget) — so the *underlying claim* ("this holds up under heavy synthetic annotation load") is directionally true even though the specific number isn't traceable to anything in code.

### LOW — Renderer-count question: the spike's own answer and the "2" assumption both need correcting
**Severity:** Low (informational — corrects the audit brief's own assumption)
**Finding:** The audit brief assumed "Spike: page canvas (pdf.js raster) + InteractiveOverlay SVG = 2." Live DOM inspection plus code reading shows this is **not quite right for `?spike=features` specifically**: `FeatureSpike.jsx:202` hardcodes `editMode` to always-true on its `<PdfjsArm>` instance. `PdfjsArm.jsx` passes `bakeAnnotations={!editMode}` to both `PdfPageCanvas` and `DetailTile` (`:656, 665`), which becomes `bakeAnnotations={false}` whenever `editMode` is true — meaning the canvas render call passes `annotationMode: pdfjsLib.AnnotationMode.DISABLE` (`PdfjsArm.jsx:133`) and **never bakes annotation pixels into the canvas raster at all**. So on the live `?spike=features` route, there is exactly **one** visible renderer for annotations (`InteractiveOverlay`'s SVG), not two — the canvas contributes zero annotation pixels, confirmed by DOM inspection (canvas raster present, but `bakeAnnotations` code path proven false).
**Production's true count (verified via code + live DOM, pen-tool-active scenario):** **3 simultaneously visible renderers**, not the "canvas + SVGAnnotationLayer + Fabric canvas" a naive count might suggest: (1) `SVGAnnotationLayer` (always-mounted SVG, all committed annotations, `PDFViewer.jsx:28946`), (2) `FabricDrawingCanvas`'s own live-preview `<svg><path>` for the single in-progress stroke (`FabricDrawingCanvas.jsx:1012-1033`, explicitly commented "same renderer (SVG) + same attrs as the committed stroke, so live and released weight are identical by construction"), and (3) `FabricDrawingCanvas`'s Fabric.js Canvas2D `<canvas>` itself, which also paints the live stroke via its own free-drawing brush (not merely an invisible hit-target — it's `pointerEvents: auto` and genuinely rasterizes). The page's own pdf.js canvas raster contributes **zero** annotation pixels in this scenario (`AnnotationMode.DISABLE`, confirmed at two call sites in `PdfjsViewerContainer.jsx:179,251`, with an explicit code comment: "baking here would double them and make erase leave baked pixels"). Live DOM check on the 120-page fixture confirmed the shape of this: one page wrapper held 4 `<canvas>` elements (1 pdf.js raster, 1 unidentified 300×150 — likely a thumbnail/minimap canvas, and 2 Fabric `canvas-container` canvases for different tool layers) and 2 `<svg viewBox="0 0 612 792">` elements (matching SVGAnnotationLayer + the live-preview SVG).
**Framing for the owner:** production's "3 renderers" is a deliberate, commented design choice (visual-parity between live-drag and committed rendering), not accidental duplication — but it is objectively more renderer layers than the spike's single-SVG approach. If renderer-count minimization is a goal, the spike's `InteractiveOverlay` pattern (author once in unscaled page-space SVG, zero JS zoom math, one hit-testable element per mark) is the right shape to converge toward — but it would need eraser/undo/export built on top of it first, at which point it stops being simpler.

### INFORMATIONAL — Zoom/virtualization/stability parity is close (where the spike genuinely does track production well)
- **Virtualization caps confirmed on both routes.** Production: `PdfjsViewerContainer.jsx:56` hardcodes `MAX_MOUNTED = 12` with a ~1.2-viewport mounting margin (`recomputeWindow`, `:549-581`) that re-centers and clamps if more than 12 pages would otherwise qualify. Spike: no hard cap constant, but the same ~1.2-viewport margin logic (`PdfjsArm.jsx:360`, `const over = vh * 1.2`) naturally kept mounted pages in the 1–16 range in every test here — never approaching "all 120 pages," but also never hitting an explicit ceiling the way production does. On a very large monitor at a very zoomed-out level, the spike's window could in principle mount more than 12 pages where production would clamp; this was not observed in practice but is a structural difference worth noting if screen real estate ever gets large enough.
- **Cursor-anchored zoom feel and coordinate stability are effectively identical.** Both routes: p50 ≈ 8.3ms / p95 ≈ 10ms / max ≈ 17ms frame times during a scripted ctrl+wheel zoom sweep (spike 120pg synthetic doc: p50 8.3, p95 10.0, max 17.6; spike SE-011 99pg real-markup doc: p50 8.3, p95 10.2, max 145 — one outlier, likely the async per-page annotation-extraction effect (`PdfjsArm.jsx:539-564`) hitching on a heavy real-markup page; production 120pg fixture: p50 8.3, p95 10.2, max 16.7). **Caveat**: per prior team learning (`reference_playwright_zoom_limitation`), synthetic Playwright wheel events cannot fully reproduce a real trackpad gesture's timing/acceleration curve — this parity should be read as "neither route stalls or drops frames under scripted input," not as a certified human-feel comparison. A human trackpad test is still the only way to confirm gesture feel.
- **Zero coordinate drift after 20 zoom in/out cycles on both routes** — canvas and SVG/annotation-layer bounding boxes were pixel-identical before and after, on both the spike (36-page package) and production (120-page fixture, scrolled to a mid-document page).
- **Zero console errors** across every test performed on both routes, including rapid-fire zoom bursts (race-condition stress) and rapid document switching (ghost-render stress, 3 cycles between a 99-page and a 36-page doc on the spike — DOM slot count and mounted-canvas count settled cleanly each time, no stale/orphaned nodes).
- **No memory leak detected in the spike** after 6 full top↔bottom scroll sweeps of the 120-page fixture: heap usage *decreased* by ~4.9MB (GC kept pace), DOM page-slot count stayed exactly 120 throughout, mounted-canvas count returned to baseline (3) after each sweep. Production's virtualization/cleanup code (multiple explicit teardown effects in `PdfjsViewerContainer.jsx` — RenderTask cancellation via `myGen !== genRef.current` guards at two independent sites, ResizeObserver disconnect, all event-listener removals, no `window.*` globals set) was independently confirmed via code but not separately memory-profiled in this pass (spike's clean result plus production's more defensive cleanup code make a production regression here unlikely, but it wasn't re-measured).
- **Race-condition guards exist on both**, structurally similar: spike uses a `myGen !== genRef.current` pattern in `PdfPageCanvas` and `DetailTile` (`PdfjsArm.jsx`, generation counter incremented per render attempt, checked after each await); production has the identical pattern in `PdfPageCanvas`/`DetailTile` plus a *second*, independent `settleGenRef` guarding the zoom-settle glide specifically (`PdfjsViewerContainer.jsx:650,662,749,770-773`) — one more guard than the spike has, for one more async path (the settle-commit re-raster) that the spike's simpler settle-timer model doesn't need to guard the same way.
- **Global cleanup on unmount**: spike's `PdfjsArm.jsx:610-614` sets a single `window.__spikePdfjs` global and correctly deletes it in the effect's cleanup (`delete window.__spikePdfjs` only if it's still this instance's api object — avoids clobbering a newer mount). No leaked globals found on either route.

## What Would Need to Happen for This to Become Viable

In order of what actually blocks a real user, not code-elegance:

1. Build a PDF write-back path into `InteractiveOverlay`'s object model (or bolt production's existing `pdfAnnotationsPdfLib.js`/`pdfNativeExport` onto it) — otherwise nothing drawn or edited can ever leave the browser tab.
2. Build undo/redo — even a minimal linear stack, before anything else, since every other editing feature depends on being able to undo a mistake.
3. Build a partial eraser — porting either `inkEraser.js` or `geometryEraser.js`'s approach onto `InteractiveOverlay`'s path-command model is plausible since both already operate on SVG path data / point arrays, which is exactly what `InteractiveOverlay.jsx`'s `cmds` arrays already are.
4. Decide whether collaboration is in scope for whatever this spike would become — if yes, it's a large, separate integration (Yjs + Supabase Realtime), not a small addition.
5. Fix the text-layer CSS-variable bug (`--total-scale-factor`/`--scale-round-x`/`--scale-round-y`) — small, mechanical, already root-caused above.
6. Separately (production-side, not spike-blocking): find or restore a UI trigger for `activeTool === 'text-select'` — currently dead code in production as far as this audit could determine.

Until items 1–4 exist, this spike is a renderer-rendering-technique reference (which it already explicitly is, per its own `NOTES.md`), not a drop-in replacement for production's annotation stack.

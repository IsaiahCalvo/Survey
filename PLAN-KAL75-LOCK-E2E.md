## Verified enforcement gaps (round-3 review; all three CONFIRMED in code this session) and the pre-approved fix

- **G1 — tool shortcuts bypass the lock.** `PDFViewer.jsx:20872-21093` registers a window BUBBLE keydown handler switching tools on plain letters (`p` → pen at `:20895`, etc.). The banner's blocker (`DocumentLockBanner.jsx:86-106`) only swallows Cmd+Z / Delete / Backspace — plain letters sail through. A locked viewer can press `p` and draw on the canvas (the canvas is never pointer-blocked; only the toolbar is).
- **G2 — undo/redo hotkeys preempt the blocker.** PDFViewer's KAL-301 undo/redo handler (`PDFViewer.jsx:2857-2890`) is `window` + `capture:true` — the SAME target and phase as the banner's blocker. Same-target listeners run in registration order; PDFViewer registers at mount, the banner only after the lock-state fetch resolves. So the undo handler runs FIRST, calls `stopImmediatePropagation`, and executes a real undo/redo — the banner's block never fires for those combos. (The banner also never lists the Cmd+Y / Ctrl+Y redo combos.) Listener-order fixes are fragile by construction; the robust fix is an execution-site guard.
- **G3 — toolbar CSS layer dead** (selector drift, established round 2).
- **G4 — selected-annotation mutation surfaces bypass everything** (round 4, verified): `SVGAnnotationLayer.jsx:~765-810` — window-bubble keydown handling Copy (`Cmd+C`, benign), Cut (`Cmd+X`, mutating) and z-order brackets (`Cmd+]`/`Cmd+[`, mutating); none in the banner blocklist. `useAnnotationContextMenu.jsx:~120-190` — right-click menu with Cut/Paste/Delete items calling the save path directly; mouse-driven, untouched by any keydown blocker or toolbar CSS. Drag-move/resize of a selected annotation is the same class of surface (pointer-driven mutation) — probed empirically in S4.

**Pre-approved fix** (one code-change task, cap → 3/6; restores the settled Phase-28 read-only matrix + the KAL-49 lock contract "locked documents are read-only in the viewer", no new product decision):
- `src/AppShell.jsx` (high-risk, standing waiver, attribute-only): `data-tool-toolbar="true"` on the tools-section container (`:1206`).
- `src/components/collab/ReadOnlyGate.css`: extend the existing rule with `body[data-readonly="true"] [data-tool-toolbar="true"]` and `… [data-undo-redo-controls="true"]` (undo/redo cluster already carries that attribute). Zoom/page-nav/back chrome live outside both containers — Phase-28 matrix preserved.
- `src/PDFViewer.jsx` (high-risk, standing waiver, branch-scoped guard lines, no refactor): `const isReadOnlyDoc = () => document.body.getAttribute('data-readonly') === 'true'` guards placed (a) at the top of `handleUndoRedoKey` (the whole handler is mutating), and (b) inside ONLY the mutating branches of the `:20872` handler — the tool-switching letters AND the `Cmd/Ctrl+V` paste branch (`:21067`, writes via `pasteAnnotationAt`) — NOT at its top, because that handler also owns Cmd+S, search, zoom, and page-nav hotkeys (`:21014-21090`) which the Phase-28 matrix explicitly keeps live. Execution-site guards are immune to listener-registration order and cover both the kal49 lock and the Phase-28 access-revoked gate.
- `src/components/SVGAnnotationLayer.jsx` (high-risk — zoom invariants UNTOUCHED; this is a keydown-handler-only edit): same guard on the MUTATING branches of the copy/cut/z-order keydown handler (`:~765-810`): Cut and bracket-reorder bail when read-only; Copy stays live (read action, matches Phase-28 "read affordances unchanged").
- `src/hooks/useAnnotationContextMenu.jsx`: suppress menu open when read-only (single guard at the open site — an annotation EDIT menu has no legitimate read-only use; keyboard Cmd+C still covers copy). If implementation reveals the menu hosts non-mutating items beyond Copy, fall back to disabling the mutating items instead; decided by minimum-diff at implementation, asserted either way in S4.
- Drag-move AND resize/rotate handles: IN CONTRACT (ticket case 16 says "editing controls/mutation actions are blocked" — moving, resizing, or rotating an annotation is a mutation action) and HARD gates, no exclusion fallback. These are TWO separate interaction entry points in the interaction layer (whole-shape move starts in the SVG pointer-down path; resize/rotate starts in the selection-handle pointer-down path and commits separately) — the pre-approved fix guards BOTH entries: bail out of the gesture start when read-only (selection-click stays live for copy); fallback if an entry and selection are inseparable: skip/revert that gesture's END commit when read-only. If no safe choke proves out within this session, the harness run stays RED and is handed off as a red run with the gap documented on the ticket — it is NOT reported green with an exclusion.

If the S4 gates unexpectedly PASS without the fix, it is not applied and the cap is untouched. Either way the ticket-close summary states plainly how case 16's clauses are met. ## Risks / mitigations

- **Native dialogs deadlock headless runs if unhandled** → global queue handler installed before any navigation; unexpected dialogs auto-dismiss + hard-fail.
- **5 s resolver TTL serves stale lock state** → page.reload between every lock-state transition + banner asserted with poll timeout ≥ 8 s.
- **Optimistic UI can mask backend truth** → every UI assertion paired with a mutation-ledger assertion (RPC recorded with exact body).
- **Menu is portalled** → query `role=menu` globally post-click, never row-scoped.
- **Foreign doc collaborator probe shape drift** → discovery run pins the exact `in.(…)` query; mock already supports `in`.
- **`alert()` on lock failure is silent-failure shaped** → any unexpected dialog fails the run loudly.
